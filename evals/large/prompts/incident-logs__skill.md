TASK. Your current directory holds six hours of logs (2026-11-06, 06:00 to 12:00 UTC) from a payments incident. The files are `logs/api.log`, `logs/auth.log`, `logs/payments.log`, `logs/db-proxy.log` and `logs/scheduler.log`, each with roughly 1,300 to 13,000 lines. There are also `deploys.csv` (4 deploys) and `config_changes.csv` (6 config changes), plus `README.md`, which defines every field you must report and the counting rule. Payments failed with database timeouts for a while that morning. Find the one change that triggered the incident, measure the incident window and how many payment requests it broke, and write `REPORT.md` in this directory. The owner wants a real root cause, not "db timeouts", so trace the chain from the change to its effect in the logs.

HOW IT WILL BE MEASURED. `REPORT.md` is checked field by field against answers worked out from the same files with the definitions in `README.md`. Read that file first and follow it to the letter. Each field sits on its own line as `FIELD: value`, in this order: `ROOT_CAUSE_CHANGE_ID:`, `ROOT_CAUSE_SERVICE:`, `INCIDENT_START_UTC:`, `INCIDENT_END_UTC:`, `FAILED_PAYMENT_REQUESTS:`, `TRIGGER_EVIDENCE:`. Both times use the format `YYYY-MM-DDTHH:MMZ` and are given in UTC. The count is a bare integer. The change id and service are spelled exactly as in the CSV. The evidence is one complete line copied byte for byte from a file in `logs/`. A value that is nearly right, such as a time one hour off, a count off by a few, or a paraphrased log line, counts as wrong. Free-form explanation may follow the fields and is read by a person.

WHAT COUNTS. The root cause is the change that started the failure chain. It is not a symptom (pool exhaustion, timeouts), not a change that merely sits near the incident, and not a later mitigation or revert. Here is an example of the evidence you want: a line in the affected service's own log that shows the triggering change taking effect, followed by the failure signature starting right after it. Two kinds of reasoning don't count. One is choosing a change because its timestamp is closest to the first error without converting the clocks. The other is blaming a service that is also logging errors without showing that its errors cause payments' errors rather than share a cause with them. At least one change other than the real trigger lands close in time and comes with its own errors, so rule out each candidate explicitly. For the count, compute the number with a script that applies the README rule. Don't estimate it, take it from `api.log`, or count only `db_timeout`.

WHAT YOU HAVE.
1. The files in this directory. `logs/` and the CSVs are read-only: never edit, move or rewrite them. The only file you create in the project is `REPORT.md`. Put scratch scripts and notes in a new `./_work/` directory.
2. Shell and file tools (Bash, Read, Edit, Write, Glob, Grep), plus Python 3 with the standard library only. There is no internet and no pip.
3. Clocks. The first line of each log is a `#` comment that states its timestamp format, and the formats differ. `api.log` uses ISO-8601 UTC with `Z`. `auth.log` uses ISO-8601 with an explicit offset (for example `-05:00`). `db-proxy.log` and `scheduler.log` use Unix epoch milliseconds. `payments.log` uses local time UTC+02:00 with no offset in the string, so subtract 2 hours. The CSVs are in UTC. Convert every timestamp to UTC before you compare anything across files, and confirm that your conversion makes each change's `config reload` or deploy line agree with its CSV time to within a few seconds.
4. A budget of 40 turns, with no one to answer questions. If something is ambiguous, follow `README.md` literally, make the most reasonable assumption, and record it under the fields.

HOW TO WORK.
1. Read `README.md` and the header line of every log, then both CSVs. Write a `./_work/notes.md` listing the candidate changes with their UTC times. Keep it updated, because you may need to reread it.
2. Write one Python script (`./_work/analyze.py`) that parses every log into UTC and prints compact summaries rather than raw dumps. It should print the UTC time of each change's log line. For each service, it should print per-minute counts of errors around those times. It should print the first and last `err=db_timeout` line in `payments.log`, converted to UTC.
3. Find the trigger. Line up, in UTC, the change times, the first change in db-proxy pool behaviour (`pool stats`, `pool exhausted`, `acquire timeout`) and the first payments `db_timeout`. Check whether a candidate's own errors began before or after the db timeouts did, and whether a revert ended the incident. The trigger should explain both the start and the end of the incident.
4. Count failures with the README rule. Group `payments.log` lines by `req`, keep the line with the highest `attempt` for each, and count the ones whose status is 5xx (any 5xx, including errors other than `db_timeout`) and whose UTC finish time falls between the start of the start minute and the end of the end minute. Lines are written when an attempt finishes, so don't assume the file is in time order. Skip the `#` header and any line that doesn't parse, but print how many lines you skipped. Sanity-check the result: print the count of first-attempt 5xx, the count of requests rescued by a retry, and the count of `402` declines, and make sure the numbers fit together.
5. Copy the evidence line by reading it out of the file with a script (for example `grep -F` of the change id), not by retyping it.
6. Write `REPORT.md`, then re-run a short check that parses its six field lines and compares each one against what your script prints.

RULES. Not allowed: (a) modifying, deleting or reformatting anything under `logs/`, `deploys.csv`, `config_changes.csv` or `README.md`; (b) using third-party packages or the network; (c) writing a field value you didn't compute or copy from the data; (d) naming more than one change as the root cause. Allowed: creating `REPORT.md` and anything under `./_work/`, running any read-only shell command, and writing as much explanation below the fields as helps.

HOW THE SESSION RUNS. You are done when `REPORT.md` exists with all six fields and they pass your re-check, or when your turns are nearly used up. In that case, write `REPORT.md` with your best values and say which ones are uncertain. Below the fields, give a timeline in UTC, the causal chain from the change to the payments failures, why each other candidate change was ruled out, and how you counted the failures, including any assumptions. Your final message should state the six values, name the key evidence and list any assumptions.
